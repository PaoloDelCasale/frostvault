### BUG-001: process_job recover branch lacks status whitelist

- **Source:** Code Review Pass 1 + Pass 2
- **Severity:** High
- Primary requirement: REQ-002
- Covers: [REQ-002/cell-RECOVER-PROCESS_JOB]
- **File:** `app/storage.py:2223-2224`
- **Disposition:** code-fix
- **Disposition rationale:** The dispatcher intentionally whitelists statuses for every peer action; recover is the only mutation path without a conjunct. Selection filtering in `process_jobs_once` is not a substitute for dispatcher defense-in-depth — especially under stale job dicts when DB status has left `{queued, retrying, restoring}`. This is a code gap against the project's own peer pattern, not a documentation misread.
- **Divergence description:** Documented/peer intent is that each `process_job` action runs only for an explicit status set. Recover executes for any non-cancelled status that reaches the branch.
- **Documented intent:** REQ-002 — recover only for `{queued, retrying, restoring}`; pending_approval must no-op.
- **Code behavior:** `elif job["action"] == "recover": process_recover(job)` with no status check (`app/storage.py:2223-2224`).
- **Expected:** `elif job["action"] == "recover" and job["status"] in {"queued", "retrying", "restoring"}:`
- **Actual:** Status-ungated recover dispatch.
- **Minimal reproduction:** Construct a job dict `action=recover`, `status=pending_approval` (or call `process_job` after DB status is `pending_approval` while dict still says `queued`); observe `process_recover` entry / RestoreObject path instead of False no-op.
- **Spec basis:** Code inconsistency with peer dispatcher guards; inferred REQ-002 from `process_job` whitelist pattern (Tier 5). Mechanical extract: `quality/mechanical/process_job_action_branches.txt`.
- **fix_type:** code
- **Proposed fix:** Add status conjunct aligned with selection + restoring poll; return False otherwise.
- **Regression test:** `quality/test_regression.py::TestBug001::test_bug_001_recover_requires_status_whitelist`
- **Patches:** `quality/patches/BUG-001-regression-test.patch`, `quality/patches/BUG-001-fix.patch`
- **Writeup:** `quality/writeups/BUG-001.md`

### BUG-002: Reversible cloud hide does not detect concurrent newer Archive Version

- **Source:** Code Review Pass 1 + Pass 2 + Pass 3
- **Severity:** High
- Primary requirement: REQ-004
- Covers: [REQ-004/cell-DETECT_CURRENT_MISMATCH-CLOUD_ARCHIVE, REQ-004/cell-DETECT_CURRENT_MISMATCH-RENAME_HIDE]
- Consolidation rationale: Both `process_cloud_archive` and `process_rename` hide-old-key issue unversioned `delete_object` without comparing the live current generation to the intended target; a shared Head/compare-or-abort helper before delete closes both cells.
- **File:** `app/storage.py:2099-2102` (primary); rename `app/storage.py:1622-1625`
- **Disposition:** code-fix
- **Disposition rationale:** Creating a delete marker requires an unversioned delete in S3, but REQ-004 still requires detecting when current ≠ scheduled generation. The code loads `provider_version_id` for the scheduled Archive Version and then never uses it for comparison — a concrete omission, not an upstream S3 limitation.
- **Divergence description:** Schedule pins `archive_version_id`; execute hides whatever is current without mismatch detection/audit.
- **Documented intent:** REQ-004 conditions — abort or audit when current key generation ≠ scheduled expectation.
- **Code behavior:** `s3_client().delete_object(Bucket=..., Key=object_key)` with no `VersionId` and no prior Head compare (`2099-2102`).
- **Expected:** Head current version (or equivalent); if ≠ scheduled `provider_version_id`, fail Job / audit actual target before marker.
- **Actual:** Silent marker on whatever is current, including a newer concurrent upload.
- **Minimal reproduction:** Schedule cloud-archive against V1; upload V2 to same key before worker runs; observe delete marker hiding V2 while Job completes narrating archival of scheduled context.
- **Spec basis:** Code inconsistency with VersionId pinning elsewhere (REQ-001/REQ-013); inferred REQ-004 Tier 5; README recovery/cleanup VersionId language.
- **fix_type:** code
- **Proposed fix:** Before unversioned delete, `head_object` current key; compare `VersionId` to scheduled `provider_version_id`; abort/audit on mismatch. Apply same helper to rename hide.
- **Regression test:** `quality/test_regression.py::TestBug002::test_bug_002_cloud_archive_detects_concurrent_version`
- **Patches:** `quality/patches/BUG-002-regression-test.patch`, `quality/patches/BUG-002-fix.patch`
- **Writeup:** `quality/writeups/BUG-002.md`

### BUG-003: List-only PostgreSQL backup verification reported as full verified success

- **Source:** Code Review Pass 1 + Pass 2
- **Severity:** High
- Primary requirement: REQ-005
- Covers: [REQ-005/cell-FULL_ISOLATED_OR_FAIL-VERIFY_RESTORE_ISOLATED, REQ-005/cell-FULL_ISOLATED_OR_FAIL-VERIFY_LATEST_CONSUMER, REQ-005/cell-MODE_DISTINGUISHED-VERIFY_LATEST_CONSUMER]
- Consolidation rationale: Producer returns success-shaped `ok: True` for list-only mode and the scheduler consumer promotes any `ok` to `status='verified'` while ignoring `verification_mode`; fixing either side alone is insufficient — both cells share one false-confidence failure mode.
- **File:** `app/services/metadata_backups.py:447-456`; consumer `app/storage.py:2578-2600`
- **Disposition:** code-fix
- **Disposition rationale:** Comment explicitly “treat as verified” on createdb failure. Consumers treat `ok` as full success. This contradicts restore-verification fitness in QUALITY.md / REQ-005; not a docs-only issue.
- **Divergence description:** TOC listing after createdb failure is recorded as verified restore success.
- **Documented intent:** REQ-005 — list-only must not equal full isolated-restore success for consumers.
- **Code behavior:** Returns `{"ok": True, "verification_mode": "pg_restore_list", ...}`; `_verify_latest_metadata_backup_once` updates `metadata_backup_runs.status='verified'` when `ok`.
- **Expected:** `ok: False` (or consumer refuses non-`temp_database` mode) so runs are not marked verified.
- **Actual:** Degraded mode still yields verified status / success metrics path.
- **Minimal reproduction:** Mock `createdb` non-zero after successful `pg_restore --list`; call `verify_restore_isolated` then consumer path; observe `ok True` and verified status update.
- **Spec basis:** `docs/metadata-backups.md` restore verification language; QUALITY Scenario 4; REQ-005.
- **fix_type:** code
- **Proposed fix:** Return `ok: False` for list-only **or** keep `ok` but make consumer require `verification_mode == "temp_database"` before setting verified.
- **Regression test:** `quality/test_regression.py::TestBug003::test_bug_003_list_only_not_full_verify`
- **Patches:** `quality/patches/BUG-003-regression-test.patch`, `quality/patches/BUG-003-fix.patch`

### BUG-004: csrf_token_for ignores session_version force-logout

- **Source:** Code Review Pass 1 + Pass 2
- **Severity:** Medium
- Primary requirement: REQ-008
- **File:** `app/sessions.py:115-137` vs `app/sessions.py:95-96`
- **Disposition:** code-fix
- **Disposition rationale:** Force-logout bumps `users.session_version`; `resolve_session` rejects skew but CSRF middleware uses `csrf_token_for`, which still returns the token. Not an end-to-end auth bypass today (endpoints use `current_user`), but REQ-008 requires parity and the gap is concrete in SQL/selection.
- **Divergence description:** Session revocation via session_version is incomplete at the CSRF layer.
- **Documented intent:** REQ-008 — CSRF lookup should return None when versions diverge, matching `resolve_session`.
- **Code behavior:** `csrf_token_for` SELECT omits session_version join/compare; returns token for non-revoked non-expired rows.
- **Expected:** None when `sessions.session_version != users.session_version`.
- **Actual:** CSRF token still returned; middleware at `main.py:289-300` can accept it.
- **Minimal reproduction:** Create session; bump user `session_version`; `resolve_session` → None; `csrf_token_for` → non-None token.
- **Spec basis:** ADR 0005 host/CSRF/reauth hardening intent; code peer `resolve_session`; REQ-008 Tier 5.
- **fix_type:** code
- **Proposed fix:** Join users and compare session_version inside `csrf_token_for` (read-only; still no last_seen touch).
- **Regression test:** `quality/test_regression.py::TestBug004::test_bug_004_csrf_honors_session_version`
- **Patches:** `quality/patches/BUG-004-regression-test.patch`, `quality/patches/BUG-004-fix.patch`
- **Writeup:** `quality/writeups/BUG-004.md`
