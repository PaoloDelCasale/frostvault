## Open Exploration Findings

### Finding G2-1: Cloud scan creates orphan Vault Files for renamed historical paths

- **Trace:** `confirm_file_rename` → `rename_file` closes current `file_paths` (`valid_to`) and inserts new path (`app/catalog.py:436-454`). Later `scan_cloud` (`app/storage.py:520-611`) still lists the old S3 key as `logical_path` and calls `record_archive_version` → `_get_or_create_file` (`catalog.py:24-58`), which joins **only** `fp.valid_to IS NULL`. The historical path no longer matches → new `vault_files` + current `file_paths` row is inserted even when `archive_versions` already exists for that `object_key`/`provider_version_id` (`catalog.py:150-183` creates first, then detects existing version and returns without cleaning the orphan).
- **Hypothesis:** After a confirmed rename, any cloud scan that still observes the old key invents a second Vault File identity for the old path, violating CONTEXT.md “Vault File identity survives confirmed renames” / Path History model.
- **Severity guess:** High (catalog identity corruption; browse/jobs may fork history).
- **Overlap with baseline:** None of BUG-001..007.

### Finding G4-1: Rename confirmations call `audit_log` without `connection`

- **Trace:** `confirm_rename` / `confirm_folder_rename` open `with db() as connection` and mutate Path History, then call `audit_log(...)` **omitting** `connection` (`main.py:1487-1501`, `1530-1546`). Auto-rename in `apply_automatic_renames` same pattern (`storage.py:801-808`). `audit_log` persists to `audit_events` only when `connection` is passed (`audit.py:9-40`); otherwise only a structured log line is emitted. `/api/audit-events` reads durable rows only.
- **Hypothesis:** Vault File / folder rename decisions never appear in the in-app audit trail despite occurring inside an open DB transaction — exactly the case the `connection=` API was designed for.
- **Severity guess:** Medium (governance/audit integrity; not data loss).
- **Overlap:** None.

### Finding G3-1: Configured S3 backup store failures become silent local-only success

- **Trace:** `backup_upgrade.main` always passes `object_store=default_object_store()` (`backup_upgrade.py:40-44`). `default_object_store` returns `None` when bucket unset **or** when `s3_client()` raises (`metadata_backups.py:88-98` bare `except Exception: return None`). `run_metadata_backup` treats `object_store is None` as success with `s3_key=None` (`666-697`) and records `status=succeeded`. Docs: “local + S3 when configured” / `system/backups/` off-host copies (`docs/metadata-backups.md:26-35,54-59`).
- **Hypothesis:** With `VAULT_S3_BUCKET` set but credentials/endpoint broken, pre-upgrade and scheduled backups report success without an off-host copy — a silent compensation failure of the backup gate.
- **Severity guess:** High (upgrade proceeds believing off-host backup exists).
- **Overlap:** Distinct from rejected former BUG-003 (list-only PostgreSQL verify semantics).

### Finding G1-1: OIDC callback switches session when identity already bound to another user

- **Trace:** Self-link / invite flows call `begin_login` storing `invite_id` (`oidc.py:108-124`). Callback `_resolve_or_bind_identity` returns an existing `user_identities` row **before** redeeming the invite (`main.py:1156-1173`). If that identity belongs to user B while the browser still has user A’s session (self-link attempt), callback else-branch `create_session` for B (`main.py:1130-1146`) — account switch instead of reject. ADR-0003: self-link attaches the acting user’s own identity; UNIQUE(issuer,subject) must not silently re-point / switch. ADR-0005: step-up refreshes the **existing** session.
- **Hypothesis:** Presenting an invite while an identity is already linked elsewhere switches the browser into the other account rather than 403 `identity_taken` / “sign out first”.
- **Severity guess:** High (session/account integrity).
- **Overlap:** Not BUG-004 (CSRF session_version).

### Finding G1-2: OIDC reauth stamps freshness without `auth_time` / `max_age`

- **Trace:** `/auth/oidc/reauth` only sets `prompt=login` (`main.py:973-990`). `_validate_id_token` checks iss/aud/exp/nonce/at_hash but never `auth_time` or `max_age` (`oidc.py:166-198`). Callback then `mark_reauthenticated` for same user (`main.py:1131-1136`). ADR-0005 claims “fresh provider login”.
- **Hypothesis:** If the IdP ignores `prompt=login` or returns a cached authentication, FrostVault still widens the reauth window — defense relies entirely on IdP honesty without token-side proof.
- **Severity guess:** Medium (depends on IdP; defense-in-depth gap).
- **Disposition lean:** Demote for adversarial unless we can show a concrete IdP-independent contract violation in-repo.

### Finding G1-3: Invite redemption lacks single-use row lock

- **Trace:** `redeem_invite` SELECT then INSERT identity then UPDATE without `WHERE redeemed_at IS NULL` or `FOR UPDATE` (`invites.py:84-107`). ADR-0003 single-use. Under PostgreSQL concurrent callbacks with different subjects can both observe `redeemed_at IS NULL` (UNIQUE is on issuer+subject, not invite row).
- **Hypothesis:** Dual bind to one target user under race.
- **Severity guess:** Medium (Postgres); Low on SQLite serialized writers.
- **Disposition lean:** Demote pending runtime stress on Postgres (baseline deferred deep migration/PG focus).

### Finding G5-1: Operators see Cancel for owner-only cloud deletion jobs

- **Trace:** UI shows Stop when `canOperate` (`static/app.js`); cancel of `cloud-archive`/`cloud-purge` requires owner (`main.py` cancel path).
- **Hypothesis:** UX mismatch → 403, not authz bypass.
- **Disposition lean:** Demote (interaction polish, not security defect).

## Pattern deep dive (gap) — Cross-implementation: identity resolution

| Path | Lookup | Creates identity? |
|------|--------|-------------------|
| Local observe | `_get_or_create_file` current path only | Yes if missing current |
| Cloud `record_archive_version` | same helper **before** object_key dedupe | Yes — orphan possible |
| Rename confirm | `rename_file` updates Path History | No new file when absorbing provisional |

**Gap:** Cloud path should resolve by existing `archive_versions.object_key` and/or historical `file_paths` before minting a Vault File.
