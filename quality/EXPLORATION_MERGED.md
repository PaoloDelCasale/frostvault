## Domain and stack (orientation)

FrostVault is a self-hosted FastAPI archive: catalog Local Copies, upload versioned Archive Versions to S3 (optionally via Rclone crypt), verify plaintext SHA-256, free local space safely, recover exact `VersionId`s, manage multi-user vault roles (owner/operator/viewer), OIDC + break-glass admin, SQLite or PostgreSQL.

Primary specs: `README.md`, `CONTEXT.md`, `docs/adr/*` (formal-spec), `docs/aws-s3-bucket.md`, `docs/filesystem-permissions.md`, `docs/metadata-backups.md`, `SECURITY.md`.

## Open Exploration Findings

1. **README vs authorization matrix disagree on who may free local space.** `README.md:19-20` states operators “can upload, free local space, and recover files,” but `app/services/vault_roles.py:32-38` documents freeing local space as an owner-only destructive lifecycle action, `app/main.py:2451-2452` enforces `is_owner`, UI flags at `app/main.py:1203` gate `delete_enabled` on ownership, and `tests/test_vault_authorization.py:470-484` asserts operators get 403 on `/api/free-space`. Product-contract drift: operators following README will hit hard failures; Phase 2 must pick one authoritative REQ.

2. **Cloud archival hides the *current* key without pinning the queued Archive Version.** `process_cloud_archive` at `app/storage.py:2099-2105` calls `delete_object(Bucket=…, Key=object_key)` with no `VersionId`, creating a delete marker on whatever is current at that key. Scheduling pins `archive_version_id` / object key at `app/services/cloud_deletion.py:359-367` and `380-405`, but a concurrent upload to the same key between queue and execute can hide a newer version than the job intended. Contrast recovery/cleanup which always pin `VersionId` (`app/storage.py:1721-1725`, `1858-1862`).

3. **Rename hide-old-key uses the same unversioned delete-marker pattern.** After verifying the new key, `process_rename` at `app/storage.py:1622-1630` deletes `old_key` without `VersionId`. Intended for S3 “rename = copy + delete marker,” but any additional concurrent write to `old_key` between copy-verify and delete is also hidden. Multi-location: rename path `1622-1630` ↔ cloud-archive path `2099-2105`.

4. **Recovery download has dual implementations with asymmetric pinning mechanisms.** `download_exact_version_plaintext` at `app/storage.py:1829-1862` uses rclone `--s3-version-id=…` for crypt/content-encrypted vaults, then falls back to boto3 `get_object(…, VersionId=…)` for plaintext. Crypt path addresses the *logical* remote path (`job['path']`) rather than the raw object key used by boto3. If rclone crypt remotes mishandle `--s3-version-id` through a wrapping remote, exact-version recovery could silently fetch the wrong ciphertext generation while still being labeled verified after digest check (digest mismatch would fail — unless wrong version happens to share digest, unlikely). Multi-location: crypt branch `1831-1842` ↔ plain branch `1858-1862`.

5. **`process_job` dispatches `recover` without a status whitelist.** At `app/storage.py:2223-2224`, recover runs for any non-cancelled status reaching the worker, unlike upload (`queued`/`retrying`), free-space (`queued`), cloud-archive (`queued`), and cloud-purge (`queued`/`pending_delay`). `process_jobs_once` at `app/storage.py:2313-2335` currently only selects queued/retrying/pending_delay(+time)/restoring, so `pending_approval` is not polled — but the dispatcher itself would execute recover if a future query or test path hands it a non-queued recover job. Multi-location: dispatcher `2219-2235` ↔ high-impact hold inside `process_recover` at `1910-1969`.

6. **CSRF lookup and session resolution are not session-version-parity.** `resolve_session` at `app/sessions.py:95-96` rejects rows whose `session_version` ≠ user's current version (force-logout), but `csrf_token_for` at `app/sessions.py:115-137` never checks `session_version`. Middleware at `app/main.py:289-300` may accept CSRF from a force-revoked-by-version session cookie; authorization still fails later in `current_user`/`resolve_session`. Residual risk: any future mutation endpoint that trusts CSRF+cookie without `resolve_session` inherits a weaker gate. Multi-location: `csrf_token_for` `115-137` ↔ `resolve_session` `70-112` ↔ middleware `289-300`.

7. **PostgreSQL metadata-backup verification degrades to “list-only” success.** In `verify_restore_isolated` / pg path at `app/services/metadata_backups.py:441-456`, if `createdb` fails, verification returns `ok: True` with `verification_mode: "pg_restore_list"` after only `pg_restore --list` succeeded. Operators may believe restore integrity was proven when only the dump TOC was readable — a silent false confidence mode for disaster-recovery fitness.

8. **Break-glass client IP depends entirely on Trusted Proxy composition.** `is_break_glass_allowed` at `app/breakglass.py:30-48` fail-closes on missing/unparseable IPs; `resolve_client_ip` at `app/proxy.py:28-48` only trusts `X-Forwarded-For` when the peer is in `TRUSTED_PROXIES`. Misconfigured `TRUSTED_PROXIES` (too wide) lets clients forge break-glass source IPs; too narrow breaks legitimate proxied admins. ADR `docs/adr/0004-break-glass-network-gating.md` + `docs/adr/0005-host-csrf-reauth-hardening.md` make this the security perimeter. Startup validates CIDR syntax (`app/config.py:194-204`) but not semantic width.

9. **Free-space safety is worker-enforced; API queue is optimistic.** `/api/free-space` at `app/main.py:2443-2458` queues after owner+reauth+flag checks only. Fingerprint/`VersionId`/integrity gates run in `process_free_space` at `app/storage.py:1705-1751` (claim via rename, rehash, restore on failure). Correct defense-in-depth, but TOCTOU windows between UI eligibility and worker execution can produce failed jobs rather than blocked queues — UI must not treat 202 as “local copy already gone.”

10. **Automatic rename identity uses digest uniqueness; ambiguity requires human confirmation.** `list_rename_candidates` at `app/catalog.py:456-509` marks `auto` only for 1:1 digest matches; `confirm_file_rename` at `app/catalog.py:511+` absorbs provisional path files into stable Vault File identity per ADR `docs/adr/0001-stable-vault-file-identity.md`. Risk: identical content copies (true duplicates) can be mis-auto-merged if presence/missing pairing is wrong under concurrent scans.

## Quality Risks

Domain: self-hosted multi-tenant archive with irreversible cloud purge, local deletion, and encrypted remotes.

1. **Silent wrong Archive Version / wrong key after concurrent writers** — Highest severity. Cloud archive and rename hide-current-key without VersionId (`app/storage.py:2099-2105`, `1622-1625`). Failure scenario: user A queues reversible archive for file F; user/process B uploads a new version to the same key; archive job creates delete marker hiding B’s version while catalog still thinks it archived A’s version context.

2. **Unauthorized destructive action via role confusion** — README advertises operator free-space (`README.md:19-20`) while code denies it (`vault_roles.py:32-38`, `main.py:2451`). Failure scenario: operators escalate support pressure to widen `is_owner` checks incorrectly, or owners assume operators already cleaned locals when they could not.

3. **Break-glass exposure behind reverse proxies** — If `TRUSTED_PROXIES` includes the public internet or a shared LB network, clients forge `X-Forwarded-For` into `BREAK_GLASS_ALLOWED_CIDRS` (`proxy.py:28-48`, `breakglass.py:30-48`). Classic self-hosted auth failure mode.

4. **Glacier RestoreObject irreversibility after acceptance** — `process_recover` at `app/storage.py:1995-2004` calls `restore_object` once AWS accepts it cannot be cancelled (messages encode this). High-impact path holds for owner approval (`1910-1969`, approve at `main.py:2395-2440`), but non-high-impact restores fire immediately — cost surprise / wrong-tier restores.

5. **Metadata backup “verified” without isolated restore** — `metadata_backups.py:447-456`. Failure scenario: production PostgreSQL host cannot `createdb`; backups marked verified; disaster recovery discovers dumps are incomplete.

6. **Job dispatcher status gaps** — Recover without status filter (`storage.py:2223-2224`) plus in-memory `cancelled_jobs` cleared only for certain statuses (`2209-2212`) risks odd re-entry if selection queries widen. Domain knowledge: queue workers that special-case statuses unevenly are a classic source of double-restore / double-delete.

7. **Crypt secret custody vs upload gate** — `require_upload_custody` at `app/services/vault_recovery.py:145-149` blocks uploads until custody confirmed; export paths must never leak secrets into audit (`vault_crypto.py:134-166`). Failure: custody confirmed without offline export actually stored → irrecoverable crypt vault after DB loss.

8. **Quota / concurrency starvation** — Fair scheduler `select_fair_jobs` (`job_scheduler.py:15-77`) interleaves vaults; operating windows reject overnight spans (`operation_policies.py:96-97`). Failure: operators expect overnight windows; jobs never run; backlog grows silently until window opens.

## Pattern Deep Dive — Fallback and Degradation Path Parity

### Cascade: exact Archive Version download

- **Primary (plain):** `download_exact_version_plaintext` boto3 `get_object` with `VersionId` — `app/storage.py:1858-1862`.
- **Fallback/alternate (crypt names or content):** rclone `copyto` with `--s3-version-id=` — `app/storage.py:1829-1855`.
- **Parity gaps:** Plain path verifies by streaming exact version bytes from object key; crypt path addresses logical `job['path']` on a runtime crypt remote. Both require `provider_version_id` (`1825-1826`) and post-hash in `process_recover` (`2040-2044`). Gap hypothesis: rclone flag propagation through crypt→s3 remote chain may not pin the same object generation as boto3 VersionId on the raw key — digest check is the only backstop.
- **Candidate requirements:** REQ-001 — both download surfaces MUST pin the same Archive Version identity; digest mismatch MUST fail the Job without promoting local presence.

### Cascade: free-space claim restore

- **Primary:** rename claim → rehash → unlink claim — `app/storage.py:1740-1753`.
- **Fallback:** `restore_claimed_local_copy` hardlink/rename back — `app/storage.py:1754-1759`, helper `1239-1257`.
- **Parity gaps:** If restore returns False, error message points at claim path (`1755-1758`) — good. If claim disappears mid-restore, raises hard error (`1251-1254`). Ensure UI surfaces claim path for operator salvage.
- **Symbols traced:** `process_free_space`, `hash_stable_regular_file`, `restore_claimed_local_copy`.

### Cascade: metadata backup verification

- **Primary:** isolated `createdb` + `pg_restore` + count query — `metadata_backups.py:458-500`.
- **Degraded:** TOC list only marked `ok: True` — `441-456`.
- **Parity gap:** degraded path does not enforce schema revision / row counts — silently weaker invariant than primary.

## Pattern Deep Dive — Dispatcher Return-Value Correctness

### `process_job` at `app/storage.py:2196-2235`

- **Input types:** action ∈ {upload, rename, recover, free-space, cloud-archive, cloud-purge}; status ∈ {queued, retrying, restoring, pending_delay, pending_approval, cancelled, …}.
- **Combinations checked:**
  - upload + queued/retrying → `process_upload` — correct.
  - recover + *any* (except cancelled short-circuit) → `process_recover` — **status filter missing** vs peers.
  - recover + restoring + age < poll interval → returns False early (`2214-2218`) — correct deferral.
  - cloud-purge + pending_delay before deadline → `process_cloud_purge` returns without work (`2136-2141`) — correct.
  - unknown action/status → returns False (`2234-2235`) without failing the job — can leave stuck rows if selection query and dispatcher diverge.
- **Candidate requirements:** REQ-002 — recover MUST only execute for an explicit status set (`queued`, `retrying`, `restoring`) matching selection; other statuses MUST no-op.
- **Symbols traced:** `process_job`, `process_recover`, `process_cloud_purge`, `process_jobs_once`.

## Pattern Deep Dive — Composition and Mount-Context Awareness

### Break-glass behind Trusted Proxy

- **Composes inside:** reverse-proxy deployments (`docs/adr/0005-host-csrf-reauth-hardening.md`).
- **Canonical representation:** client IP after stripping trusted hops — `resolve_client_ip` `proxy.py:40-48`.

- **Drift scenario:** peer is a trusted proxy but `X-Forwarded-For` is client-controlled with an extra trusted hop inserted; algorithm returns first untrusted from the right — generally correct, but if *all* hops are trusted, returns `hops[0]` (`48`) which may still be a proxy, not the client.
- **Observable failure:** break-glass allowed/denied for the wrong address; audit logs wrong IP.
- **Symbols traced:** `resolve_client_ip`, `is_break_glass_allowed`, `_client_ip` in `main.py:254-260`.

## Open Exploration Findings

### Finding G2-1: Cloud scan creates orphan Vault Files for renamed historical paths

- **Trace:** `confirm_file_rename` → `rename_file` closes current `file_paths` (`valid_to`) and inserts new path (`app/catalog.py:436-454`). Later `scan_cloud` (`app/storage.py:520-611`) still lists the old S3 key as `logical_path` and calls `record_archive_version` → `_get_or_create_file` (`catalog.py:24-58`), which joins **only** `fp.valid_to IS NULL`. The historical path no longer matches → new `vault_files` + current `file_paths` row is inserted even when `archive_versions` already exists for that `object_key`/`provider_version_id` (`catalog.py:150-183` creates first, then detects existing version and returns without cleaning the orphan).
- **Hypothesis:** After a confirmed rename, any cloud scan that still observes the old key invents a second Vault File identity for the old path, violating CONTEXT.md “Vault File identity survives confirmed renames” / Path History model.
- **Severity guess:** High (catalog identity corruption; browse/jobs may fork history).
- **Overlap with baseline:** None of BUG-001..007.

### Finding G4-1: Rename confirmations call `audit_log` without `connection`

- **Trace:** `confirm_rename` / `confirm_folder_rename` open `with db() as connection` and mutate Path History, then call `audit_log(...)` **omitting** `connection` (`main.py:1487-1501`, `1530-1546`). Auto-rename in `apply_automatic_renames` same pattern (`storage.py:801-808`). `audit_log` persists to `audit_events` only when `connection` is passed (`audit.py:9-40`); otherwise only a structured log line is emitted. `/api/audit-events` reads durable rows only.
- **Hypothesis:** Vault File / folder rename decisions never appear in the in-app audit trail despite occurring inside an open DB transaction — exactly the case the `connection=` API was designed for.
- **Severity guess:** Medium (governance/audit integrity; not data loss).
- **Overlap:** None.

### Finding G3-1: Configured S3 backup store failures become silent local-only success

- **Trace:** `backup_upgrade.main` always passes `object_store=default_object_store()` (`backup_upgrade.py:40-44`). `default_object_store` returns `None` when bucket unset **or** when `s3_client()` raises (`metadata_backups.py:88-98` bare `except Exception: return None`). `run_metadata_backup` treats `object_store is None` as success with `s3_key=None` (`666-697`) and records `status=succeeded`. Docs: “local + S3 when configured” / `system/backups/` off-host copies (`docs/metadata-backups.md:26-35,54-59`).
- **Hypothesis:** With `VAULT_S3_BUCKET` set but credentials/endpoint broken, pre-upgrade and scheduled backups report success without an off-host copy — a silent compensation failure of the backup gate.
- **Severity guess:** High (upgrade proceeds believing off-host backup exists).
- **Overlap:** Distinct from rejected former BUG-003 (list-only PostgreSQL verify semantics).

### Finding G1-1: OIDC callback switches session when identity already bound to another user

- **Trace:** Self-link / invite flows call `begin_login` storing `invite_id` (`oidc.py:108-124`). Callback `_resolve_or_bind_identity` returns an existing `user_identities` row **before** redeeming the invite (`main.py:1156-1173`). If that identity belongs to user B while the browser still has user A’s session (self-link attempt), callback else-branch `create_session` for B (`main.py:1130-1146`) — account switch instead of reject. ADR-0003: self-link attaches the acting user’s own identity; UNIQUE(issuer,subject) must not silently re-point / switch. ADR-0005: step-up refreshes the **existing** session.
- **Hypothesis:** Presenting an invite while an identity is already linked elsewhere switches the browser into the other account rather than 403 `identity_taken` / “sign out first”.
- **Severity guess:** High (session/account integrity).
- **Overlap:** Not BUG-004 (CSRF session_version).

### Finding G1-2: OIDC reauth stamps freshness without `auth_time` / `max_age`

- **Trace:** `/auth/oidc/reauth` only sets `prompt=login` (`main.py:973-990`). `_validate_id_token` checks iss/aud/exp/nonce/at_hash but never `auth_time` or `max_age` (`oidc.py:166-198`). Callback then `mark_reauthenticated` for same user (`main.py:1131-1136`). ADR-0005 claims “fresh provider login”.
- **Hypothesis:** If the IdP ignores `prompt=login` or returns a cached authentication, FrostVault still widens the reauth window — defense relies entirely on IdP honesty without token-side proof.
- **Severity guess:** Medium (depends on IdP; defense-in-depth gap).
- **Disposition lean:** Demote for adversarial unless we can show a concrete IdP-independent contract violation in-repo.

### Finding G1-3: Invite redemption lacks single-use row lock

- **Trace:** `redeem_invite` SELECT then INSERT identity then UPDATE without `WHERE redeemed_at IS NULL` or `FOR UPDATE` (`invites.py:84-107`). ADR-0003 single-use. Under PostgreSQL concurrent callbacks with different subjects can both observe `redeemed_at IS NULL` (UNIQUE is on issuer+subject, not invite row).
- **Hypothesis:** Dual bind to one target user under race.
- **Severity guess:** Medium (Postgres); Low on SQLite serialized writers.
- **Disposition lean:** Demote pending runtime stress on Postgres (baseline deferred deep migration/PG focus).

### Finding G5-1: Operators see Cancel for owner-only cloud deletion jobs

- **Trace:** UI shows Stop when `canOperate` (`static/app.js`); cancel of `cloud-archive`/`cloud-purge` requires owner (`main.py` cancel path).
- **Hypothesis:** UX mismatch → 403, not authz bypass.
- **Disposition lean:** Demote (interaction polish, not security defect).
