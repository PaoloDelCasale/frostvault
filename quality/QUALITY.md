# Quality Constitution: FrostVault

> Generated by [Quality Playbook](https://github.com/andrewstellman/quality-playbook) v1.5.6 — Andrew Stellman
> Date: 2026-07-23 · Project: FrostVault

## Purpose

FrostVault quality means **exact Archive Versions stay recoverable after Local Copies are deleted**, authorization matches the role matrix, and irreversible cloud/local actions cannot be triggered by forged identity, wrong job status, or optimistic UI success. Quality is built into requirements, fitness scenarios, and protocols that every AI session inherits (**Deming**), not bolted on as a post-hoc test pass rate.

**Fitness for use (Juran)** for this system: an owner can free local space only when a verified VersionId still exists and the worker can prove it; recoveries restore that same generation through both boto3 and rclone crypt paths; break-glass stays unreachable except from intended networks; metadata “verified” means isolated restore, not a misleading TOC list. “Tests pass” is necessary but not sufficient — silent wrong-version hide or false backup confidence fails fitness even when HTTP returns 200/202.

**Quality is free (Crosby)** relative to production failure modes here: a single wrong delete marker on a concurrent upload, or a falsely verified PostgreSQL dump, costs more operator hours and trust than maintaining these scenarios and protocols up front.

## Coverage Targets

| Subsystem | Target | Why |
|-----------|--------|-----|
| `app/storage.py` job/recovery/free-space/cloud paths | 90–95% | Concurrent hide + VersionId pinning bugs lose Archive Versions with weak detection |
| AuthN/AuthZ (`sessions`, `proxy`, `breakglass`, `vault_roles`, HTTP gates) | 90–95% | Forged XFF / role confusion enables break-glass or destructive actions |
| Cloud deletion scheduling (`cloud_deletion.py`) | 85–90% | Queue vs execute VersionId mismatch is a silent integrity failure |
| Metadata backups | 85–90% | List-only “ok: True” creates false DR confidence |
| Catalog identity / rename | 80–85% | Ambiguous digest auto-merge corrupts stable Vault File identity |
| DB adapters / schema gate | 80% | Stale schema or SQLite/PG divergence corrupts metadata |
| Config / policies / scheduler | 75–80% | Overnight window rejection and fair scheduling affect operability more than integrity |

## Coverage Theater Prevention

Project-specific fake tests to reject:

- Asserting `process_job` returned True without checking whether `process_recover` / S3 calls occurred for a given status
- Checking HTTP 202 on `/api/free-space` without asserting no Job for operators / Local Copy still present until worker success
- Mocking `s3_client().delete_object` and only asserting it was called — without asserting VersionId presence/absence against the requirement under test
- Asserting `verification_mode` key exists without asserting consumers cannot treat `pg_restore_list` as full verify
- Asserting `resolve_client_ip` returned a string without checking peer-trust / hop selection
- Import-only or “no exception” tests around `download_exact_version_plaintext`

## Fitness-to-Purpose Scenarios

### Scenario 1: Concurrent upload hidden by unversioned archive delete

**Requirement tag:** [Req: inferred — VersionId pinning parity]

**What happened:** Because `process_cloud_archive` issues `delete_object(Bucket, Key)` without VersionId (`app/storage.py:2099-2102`), a Job scheduled against Archive Version V1 can create a delete marker that hides V2 if V2 was uploaded to the same key between queue and execute. Catalog/audit may still narrate archival of the queued context while V2 becomes unreachable via current-key GETs — a silent integrity failure across potentially terabytes of Archive Versions with no digest mismatch signal (nothing was downloaded).

**The requirement:** Execute path must detect mismatch against scheduled `archive_version_id` / expected generation or abort and audit the actual marker target (REQ-004).

**How to verify:** `TestFitnessScenarios.test_scenario_1_cloud_archive_delete_object_omits_version_id` (source inspection of call shape) + Phase 3 concurrent integration when S3 available.

---

### Scenario 2: Operator free-space advertised but denied

**Requirement tag:** [Req: formal — vault_roles + tests; README conflict]

**What happened:** README Users section claims operators can free local space (`README.md:19-20`) while `is_owner` + `/api/free-space` + tests deny it. Operators following docs hit 403; support pressure can incorrectly widen owner checks — the highest-likelihood path to unauthorized Local Copy deletion.

**The requirement:** Code/tests remain owner-only; docs compensate (REQ-003).

**How to verify:** `TestSpecRequirements.test_req_003_operator_not_owner` and README conflict source assertion.

---

### Scenario 3: Recover dispatcher status gap enables side effects

**Requirement tag:** [Req: inferred — process_job whitelist]

**What happened:** `process_job` runs recover for any non-cancelled status (`app/storage.py:2223-2224`) unlike upload/free-space peers. If selection ever returns `pending_approval`, RestoreObject can fire despite high-impact holds (`process_recover` ~1910+), creating uncancelable AWS cost and wrong-tier restores.

**The requirement:** Explicit recover status whitelist (REQ-002).

**How to verify:** `TestSpecRequirements.test_req_002_recover_branch_lacks_status_conjunct` + mechanical `quality/mechanical/verify.sh`.

---

### Scenario 4: Metadata backup false confidence

**Requirement tag:** [Req: inferred — verify_restore_isolated degradation]

**What happened:** When `createdb` fails, verification returns `ok: True` with `verification_mode: "pg_restore_list"` (`metadata_backups.py:447-456`). Operators see success after TOC list only; disaster recovery discovers dumps never restored into an isolated DB — hours of outage multiplied by false confidence.

**The requirement:** List-only must not equal full verify for consumers (REQ-005).

**How to verify:** `TestFitnessScenarios.test_scenario_4_list_only_mode_marked_in_source`.

---

### Scenario 5: Break-glass behind over-wide Trusted Proxies

**Requirement tag:** [Req: formal — ADR 0004/0005]

**What happened:** If `TRUSTED_PROXIES` includes client-reachable networks, clients forge `X-Forwarded-For` into `BREAK_GLASS_ALLOWED_CIDRS`. `resolve_client_ip` + `is_break_glass_allowed` then admit the emergency password path from the public internet — classic self-hosted auth failure.

**The requirement:** XFF only from trusted peers; fail-closed IP checks (REQ-006, REQ-007).

**How to verify:** `TestFitnessScenarios.test_scenario_5_untrusted_peer_ignores_xff` and break-glass deny tests.

---

### Scenario 6: Free-space claim without restore loses Local Copy

**Requirement tag:** [Req: formal — README Local cleanup safety]

**What happened:** Without claim restore (`restore_claimed_local_copy`), a failed rehash after rename leaves the only Local Copy off the stable path. At vault scale (thousands of files), even rare failures become permanent local loss with cloud still holding the version — operators cannot browse/open until manual salvage from claim path.

**The requirement:** Restore or hard-error with claim path (REQ-009).

**How to verify:** `TestFitnessScenarios.test_scenario_6_restore_claimed_helper_exists`.

---

### Scenario 7: Crypt vs plain VersionId pin asymmetry

**Requirement tag:** [Req: formal — recovery VersionId]

**What happened:** Plain path pins boto3 VersionId on `object_key`; crypt path pins rclone `--s3-version-id` on logical `job['path']`. If flag propagation through crypt→s3 remotes fails, wrong ciphertext generation could be fetched; digest check is the only backstop. Wrong generation with identical content (rare) could pass — wrong provenance in catalog linkage.

**The requirement:** Both surfaces require VersionId; digest failure must not promote presence (REQ-001).

**How to verify:** `TestSpecRequirements.test_req_001_version_id_required_and_pinned_in_source`.

---

### Scenario 8: CSRF accepts force-revoked session version

**Requirement tag:** [Req: inferred — session_version parity]

**What happened:** `resolve_session` rejects mismatched `session_version`; `csrf_token_for` does not. Middleware may accept CSRF from a force-revoked cookie before auth fails later. Residual risk: future mutation endpoints that trust CSRF+cookie without `resolve_session` inherit a weaker gate.

**The requirement:** CSRF lookup honors session_version (REQ-008).

**How to verify:** `TestFitnessScenarios.test_scenario_8_csrf_query_omits_session_version`.

---

### Scenario 9: Overnight operating window silently invalid

**Requirement tag:** [Req: inferred — operation_policies]

**What happened:** Owners expect overnight windows (`22:00`–`06:00`); `_normalize_windows` rejects `start >= end`. Misunderstood UX yields empty effective windows; fair scheduler backlog grows until someone notices jobs never enter the window — silent operability failure.

**The requirement:** Reject overnight single-day spans with clear error (REQ-012).

**How to verify:** `TestBoundaries.test_operating_window_rejects_overnight_span`.

---

### Scenario 10: Stale schema boots into undefined behavior

**Requirement tag:** [Req: formal — database schema gate]

**What happened:** Without `HEAD_SCHEMA_REVISION` enforcement, a process on migration N-1 can write rows missing columns expected by code paths (e.g., local retention), corrupting metadata backups and job rows across an entire deployment.

**The requirement:** Refuse start unless alembic head matches (REQ-010).

**How to verify:** `TestSpecRequirements.test_req_010_head_schema_constant`.

## AI Session Quality Discipline

1. Read `quality/QUALITY.md` and `quality/REQUIREMENTS.md` before changing auth, storage jobs, or cloud deletion.
2. Run `.venv/bin/python -m unittest discover -s tests -v` (and quality functional tests) before marking work complete.
3. Add tests for new irreversible actions (free-space, purge, recover, break-glass) including deny paths.
4. Update this file when new failure modes are discovered — never remove scenarios.
5. Output a Quality Compliance Checklist before ending a session.
6. Do not “fix” README/role conflicts by silently widening `is_owner` checks.

## The Human Gate

- Whether product intent is owner-only free-space vs README Users wording (spec vs code disposition)
- Semantic width of `TRUSTED_PROXIES` / break-glass CIDRs in a real network
- Acceptable cost/risk for Glacier RestoreObject without high-impact hold
- Whether cloud-archive should pin VersionId vs re-resolve current with audit (product decision)
- UX for operating windows that must span midnight
- Production crypt key custody procedures beyond the upload gate
