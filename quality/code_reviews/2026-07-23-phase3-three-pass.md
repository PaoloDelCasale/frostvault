## Pass 1: Structural Review

Structural correctness only — no requirement lens.

### app/storage.py

- **Line 2223-2224:** [BUG] `process_job` dispatches `recover` with no status conjunct.
  Peers gate upload/rename/free-space/cloud-* on explicit status sets. Expected: recover
  only for `{queued, retrying, restoring}`. Actual: any non-cancelled job reaching the
  branch calls `process_recover`. Matter: double-execution / pending_approval side-effect
  hazard if selection widens or status races leave a stale queued dict while DB is
  `downloading`/`pending_approval`.

- **Line 2099-2102:** [BUG] `process_cloud_archive` calls `delete_object(Bucket, Key)`
  without comparing the live current `VersionId` to the scheduled
  `archive_versions.provider_version_id` loaded at 2087-2093. Expected: abort or audit
  when current ≠ scheduled. Actual: unversioned delete always hides whatever is current.
  Matter: concurrent upload between schedule and execute is silently hidden.

- **Line 1622-1625:** [BUG] `process_rename` hide-old-key uses the same unversioned
  `delete_object` pattern without current-generation detection (same hazard class as
  cloud-archive).

- **Line 2578-2600:** [BUG] `_verify_latest_metadata_backup_once` promotes a backup run to
  `status='verified'` whenever `result.get("ok")` is truthy. It never inspects
  `verification_mode`. Combined with list-only `ok: True` at
  `metadata_backups.py:447-456`, TOC-only checks are recorded as full verification.

### app/services/metadata_backups.py

- **Line 447-456:** [BUG] On `createdb` failure after successful `pg_restore --list`,
  returns `ok: True` with `verification_mode: "pg_restore_list"`. Comment says “treat as
  verified”. Expected for fitness: non-success for isolated-restore consumers, or
  consumers must refuse list-only. Actual: success-shaped result.

### app/sessions.py

- **Line 115-137:** [BUG] `csrf_token_for` selects only expiry/revocation fields and
  returns `csrf_token` without joining/comparing `users.session_version`.
  `resolve_session` at 95-96 rejects version skew. Expected defense-in-depth parity.
  Actual: force-logout via session_version bump still yields a CSRF token that middleware
  at `main.py:289-300` will accept.

### app/main.py / README.md

- **README.md:19-20 vs main.py:2451:** [BUG] Users section documents operator free-space;
  HTTP gate requires `is_owner`. Spec/docs inconsistency (not an authz bypass in code).

### app/proxy.py / app/breakglass.py

Reviewed `resolve_client_ip` and `is_break_glass_allowed` bodies for null/fail-closed
behavior, CIDR parsing, and XFF hop walk. No confirmed structural bugs: missing peer →
None; untrusted peer ignores XFF; loopback always allowed; empty CIDRs deny public IPs.

### app/services/vault_roles.py

Role helpers match owner/operator/viewer matrix. No structural defect.

### QUESTION (not promoted)

- **storage.py:1829-1862:** Whether rclone crypt remotes honor `--s3-version-id` through
  the crypt→S3 chain identically to boto3 `VersionId` is unverified without a versioned
  crypt integration fixture. Code pins the flag; digest check is the backstop.
  Classification: unverified risk / rejected as confirmed bug (CAND-006).

## Pass 2: Requirement Verification

### REQ-001: Exact Archive Version recovery must pin provider VersionId
**Status**: SATISFIED
**Evidence**: `app/storage.py:1825-1826` raises without VersionId; `:1830` crypt flag;
`:1858-1861` boto3 `VersionId=`; `:2040-2044` digest mismatch fails Job.
**Analysis**: All three download surfaces pin. Runtime rclone crypt propagation remains
an unverified integration risk, not a code-absence violation.

### REQ-002: Job dispatcher must gate each action on an explicit status set
**Status**: VIOLATED
**Evidence**: `app/storage.py:2223-2224` — `elif job["action"] == "recover":` with no
status conjunct; peers at 2219-2232 have explicit sets.
**Analysis**: recover + pending_approval / non-poll statuses are not refused by the
dispatcher itself. `process_jobs_once` currently filters selection, but defense-in-depth
and stale-status races remain.
**Severity**: High — can re-enter `process_recover` (RestoreObject / download) outside
intended statuses.

### REQ-003: Free local space is owner-only
**Status**: PARTIALLY SATISFIED
**Evidence**: Code SATISFIED — `vault_roles.py:32-38`, `main.py:2451`; Docs VIOLATED —

## Pass 3: Cross-Requirement Consistency

### Shared Concept: VersionId policy
**Requirements**: REQ-001, REQ-004, REQ-013
**What REQ-001 claims**: Recovery must pin VersionId on every download surface.
**What REQ-004 claims**: Reversible hide must not silently affect unexpected newer generation.
**What REQ-013 claims**: Purge deletes pin VersionId.
**Consistency**: INCONSISTENT (implementation)
**Code evidence**: Recovery/purge pin VersionId; cloud-archive/rename hide use unversioned
`delete_object` without mismatch detection.
**Impact**: Archive Version identity is strong on recover/purge and weak on reversible hide.
**Analysis**: Intentional S3 delete-marker mechanics require unversioned delete to create a
marker, but REQ-004 still requires detection/audit — currently absent.

### Shared Concept: Free-space authorization
**Requirements**: REQ-003, REQ-016, README Users
**Consistency**: INCONSISTENT (docs vs code)
**Code evidence**: `is_owner` for free-space; `can_operate` for upload/recover; README Users
lists free-space under operator capabilities.
**Impact**: Operators following README hit 403; risk of incorrectly widening code.

### Shared Concept: Session revocation
**Requirements**: REQ-008 vs resolve_session used by authz
**Consistency**: INCONSISTENT (layers)
**Code evidence**: `resolve_session` honors session_version; `csrf_token_for` does not.
**Impact**: CSRF middleware can accept tokens for force-logged-out sessions; API auth still
fails closed via `current_user`.

### Shared Concept: Backup verification strength
**Requirements**: REQ-005 vs docs/metadata-backups.md “restore verification”
**Consistency**: INCONSISTENT
**Code evidence**: list-only `ok: True` + consumer `status='verified'`.
**Impact**: Operators believe dumps were restore-proven when only TOC listing succeeded.

### Shared Concept: Proxy trust composition
**Requirements**: REQ-006 ∩ REQ-007
**Consistency**: CONSISTENT
**Code evidence**: Break-glass uses `resolve_client_ip`; untrusted peers cannot forge XFF.
**Analysis**: Composition is correct; residual risk is operator misconfiguration of
`TRUSTED_PROXIES` (design/ops, not code defect).
