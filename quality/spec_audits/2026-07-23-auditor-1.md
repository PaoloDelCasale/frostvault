# Spec Audit Report — Auditor 1 (claude-opus-4-8)

Date: 2026-07-23
Secondary emphasis: authorization, input validation, dispatch/enumeration logic

## Findings

### app/storage.py

- **Line 2223-2224:** DIVERGENT [Req: REQ-002 — Tier 5] `process_job` recover branch has no status conjunct, unlike every peer action.
  Spec says: recover must execute only for an explicit status set (`queued`, `retrying`, `restoring`); other statuses (e.g. `pending_approval`) must no-op with no `process_recover`/`RestoreObject`.
  Code does: `elif job["action"] == "recover": process_recover(job)` runs for *any* status that reaches the branch (only `cancelled` is short-circuited at line 2206). Peers gate explicitly — upload `{queued, retrying}` (2219), rename `queued` (2221), free-space `queued` (2225), cloud-archive `queued` (2227), cloud-purge `{queued, pending_delay}` (2229-2232). `process_jobs_once` currently only selects `queued/retrying/pending_delay/restoring` (2323-2334, 2350), so the gap is latent, but the dispatcher itself would fire recover (and thus `restore_object` at 1996) if a widened selection query or test path ever hands it a non-poll-eligible recover row. Defense-in-depth gate is missing.
  Confidence: high (the missing conjunct is definitive; requirement itself is Tier 5 inferred — NEEDS REVIEW on product intent).

- **Line 2099-2102:** DIVERGENT [Req: REQ-004 — Tier 5] `process_cloud_archive` issues an unversioned `delete_object` with no concurrent-generation detection.
  Spec says: cloud-archive must not hide a newer concurrent generation than the Job scheduled — it must load the scheduled `archive_version_id`, and if the current key generation differs, abort or audit the actual marker target.
  Code does: it *reads* `provider_version_id` for the scheduled version (2088) but never uses it. It calls `s3_client().delete_object(Bucket=..., Key=object_key)` with no `VersionId` and no `head_object`/generation comparison, then records whatever marker VersionId S3 returns (2103-2116). A version uploaded to the same key between queue and execute is silently hidden with no digest-mismatch signal, while the catalog/audit narrate the queued context. Contrast cloud-purge, which pins `VersionId` on every delete (2164).
  Confidence: medium-high (requirement is Tier 5 inferred; the unversioned call and unused pin are definitive — NEEDS REVIEW on whether product wants VersionId pin vs re-resolve+audit).

- **Line 1622-1625:** DIVERGENT [Req: REQ-004 — Tier 5] `process_rename` hide-old-key shares the same unversioned-delete hazard class.
  Spec says: reversible hide (rename included) must not silently hide an unexpected newer version without detection/audit (REQ-004 CoS 4).
  Code does: after verifying the new key, it deletes `old_key` via `delete_object(Bucket=..., Key=old_key)` with no `VersionId`; any concurrent write to `old_key` between copy-verify and delete is hidden without detection. Same class as the cloud-archive path.
  Confidence: medium (Tier 5 inferred — NEEDS REVIEW).

### app/services/metadata_backups.py

- **Line 447-456:** DIVERGENT [Req: REQ-005 — Tier 5] `createdb` failure returns `ok: True` and the consumer treats it as a full verified restore.
  Spec says: when `createdb` fails after `pg_restore --list` succeeds, the outcome must not be consumed as isolated-restore success; a consuming UI must not treat `pg_restore_list` as "fully verified".
  Code does: `_verify_postgres_dump_isolated` returns `{"ok": True, ..., "verification_mode": "pg_restore_list"}` on `createdb` failure (447-456). The only consumer, `app/storage.py:_verify_latest_metadata_backup_once`, checks only `result.get("ok")` (`app/storage.py:2578`) and then sets `metadata_backup_runs.status='verified'` (`app/storage.py:2593`) regardless of `verification_mode`. A TOC-list-only degrade is therefore promoted to the same "verified" status as a real isolated restore — the exact false-DR-confidence failure mode.
  Confidence: medium-high (code-path proof that list-only is consumed as verified is definitive; requirement is Tier 5 inferred).

### app/sessions.py

- **Line 115-137:** MISSING [Req: REQ-008 — Tier 5] `csrf_token_for` omits the `session_version` revocation check that `resolve_session` enforces.
  Spec says: a force-logout via user `session_version` bump should invalidate CSRF acceptance equivalently to `resolve_session` rejection.
  Code does: `csrf_token_for` selects only `csrf_token, revoked_at, idle_expires_at, absolute_expires_at` (123-128) and rejects on revoked/expired only; it never joins `users.session_version`, unlike `resolve_session` which returns `None` when `row["session_version"] != user["session_version"]` (95-96). The CSRF middleware at `app/main.py:293` therefore accepts the CSRF token of a version-revoked (force-logged-out) session cookie that is still within its idle/absolute window and not row-`revoked_at`. Current endpoints still fail later in `current_user`/`resolve_session`, but the defense-in-depth parity the requirement asks for is absent.
  Confidence: medium (Tier 5 inferred should-exist — NEEDS REVIEW).

### app/services/operation_policies.py

- **Line 96-97:** DIVERGENT [Req: REQ-012 — Tier 3] Operating-window start/end are compared as lexicographic strings, not as `HH:MM` times, diverging from the runtime comparator.
  Spec says: `_normalize_windows` must reject `start >= end` (no overnight single-day spans); `start > end → ValueError`, valid `start < end` accepted.
  Code does: after int-parsing hours/minutes for shape validation (90-95), it discards the parsed values and compares the raw strings: `if start >= end: raise ValueError(...)` (96-97), storing the raw strings (98). Runtime matching instead parses to `time` via `_parse_hhmm` (`app/services/job_scheduler.py:107-109`). Because the shape check never enforces zero-padded two-digit hours, a non-padded input diverges: e.g. `start="9:30", end="10:00"` is a valid morning window but is rejected (`"9:30" >= "10:00"` is True), and `start="10:00", end="9:30"` (start after end) is wrongly accepted (`"10:00" >= "9:30"` is False), bypassing the REQ-012 `start > end` guard. The comment at line 89 claims to "Validate HH:MM shape" but neither enforces the padded shape nor uses a shape-safe comparison.
  Confidence: medium (depends on callers supplying non-zero-padded times; the string/time comparison inconsistency versus `_parse_hhmm` is definitive).
