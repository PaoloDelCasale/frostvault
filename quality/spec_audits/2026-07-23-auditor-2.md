### app/storage.py
- **Line 1028:** DIVERGENT [Req: REQ-009 — tier 3] Startup cleanup deletes every `is_restore_temporary_name()` entry, and that predicate includes `.cleanup-*.tmp` claim files at lines 353-357.
  Spec says: after a free-space claim, failed or interrupted verification must restore the Local Copy or surface a salvageable claim path.
  Code does: `cleanup_abandoned_restore_files()` unlinks the cleanup claim before reconciliation, destroying the only salvage copy after a crash between `local_path.rename(claimed_path)` and `claimed_path.unlink()`.
  Confidence: high

- **Line 1092:** DIVERGENT [Req: REQ-009 — tier 3] Restart reconciliation treats an absent stable path during `free-space` cleanup as completed deletion.
  Spec says: a claimed Local Copy must be reverified/unlinked only on the normal success path, and failure paths must restore or preserve a claim path.
  Code does: if the target path is missing, it marks the Local Copy missing and the Job completed at lines 1092-1109, without checking whether a `.cleanup-*.tmp` claim exists, without rehashing it, and without calling `restore_claimed_local_copy()`.
  Confidence: high

- **Line 1349:** DIVERGENT NEEDS REVIEW [Req: REQ-001 — tier 3] Upload records an Archive Version by unversioned `HeadObject` after `rclone copyto`.
  Spec says: FrostVault uploads verified Archive Versions into versioned S3 and later relies on the exact `provider_version_id` for cleanup/recovery.
  Code does: after writing the key at lines 1321-1346, it calls `head_object(Bucket, Key)` at line 1349 and records `head.get("VersionId")` at lines 1368-1373; a concurrent writer to the same S3 key can become current between upload and head, so the catalog can pin the wrong generation.
  Confidence: medium

- **Line 1398:** DIVERGENT NEEDS REVIEW [Req: REQ-001 — tier 3] Upload verification downloads by current path, not by the recorded VersionId.
  Spec says: Archive Version verification must prove the exact version that will authorize later local cleanup/recovery.
  Code does: after recording `provider_version_id`, verification calls `_download_plaintext_for_verification()` at line 1398; that helper uses rclone `copyto` from the logical/current path at lines 1278-1296 with no `--s3-version-id`, so a concurrent current-key change can verify a different generation than the cataloged VersionId.
  Confidence: medium

- **Line 1544:** DIVERGENT NEEDS REVIEW [Req: REQ-001 — tier 3] Rename records the copied new-key Archive Version by unversioned `HeadObject`.
  Spec says: Archive Versions retain the cloud key used at upload time and must remain exact VersionId identities across rename history.
  Code does: after rename `copyto` at lines 1523-1542, it calls `head_object(Bucket, Key=new_key)` at line 1544 and records that current VersionId at lines 1563-1568, so a concurrent writer to `new_key` can be cataloged as the rename copy.
  Confidence: medium

- **Line 1622:** DIVERGENT NEEDS REVIEW [Req: REQ-004 — tier 5] Rename hides the old key with an unversioned delete marker.
  Spec says: reversible hide must not silently hide an unexpected newer generation; rename hide-old-key shares the same concurrent-writer hazard.
  Code does: after verifying the new key, it calls `delete_object(Bucket, Key=old_key)` at lines 1622-1625, records only the returned marker at lines 1634-1641, and never checks that the current old-key generation still matches the scheduled prior Archive Version.
  Confidence: high

- **Line 2099:** DIVERGENT NEEDS REVIEW [Req: REQ-004 — tier 5] Cloud archive loads the scheduled Archive Version but deletes the current key without VersionId.
  Spec says: a cloud-archive Job scheduled against a specific `archive_version_id` must abort or explicitly audit mismatch if a newer generation becomes current before execution.
  Code does: it loads `object_key, provider_version_id` for the job version at lines 2086-2093, ignores the loaded `provider_version_id`, calls `delete_object(Bucket, Key=object_key)` at lines 2099-2102, and records only the delete marker at lines 2109-2124.
  Confidence: high

- **Line 2223:** DIVERGENT NEEDS REVIEW [Req: REQ-002 — tier 5] The recover dispatcher lacks an action/status whitelist.
  Spec says: recover should execute only for explicit statuses aligned with selection (`queued`, `retrying`, `restoring`) and must no-op for holds such as `pending_approval`.

  Confidence: high
