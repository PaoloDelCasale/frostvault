## Findings

### app/storage.py

- **Lines 2223–2224:** DIVERGENT [Req: REQ-002 — tier 5] `process_job` `recover` branch
  executes `process_recover(job)` for any non-cancelled status, with no status whitelist.
  Every peer action has an explicit guard:
  - `upload` requires `status in {"queued", "retrying"}` (line 2219)
  - `rename` requires `status == "queued"` (line 2221)
  - `free-space` requires `status == "queued"` (line 2225)
  - `cloud-archive` requires `status == "queued"` (line 2227)
  - `cloud-purge` requires `status in {"queued", "pending_delay"}` (lines 2229–2232)

  `elif job["action"] == "recover":` at line 2223 carries no such conjunct.
  The fresh-DB status read at lines 2199–2213 only updates `job["status"]` when
  `current["status"]` is in `{"queued", "retrying", "restoring"}` (line 2208); if the
  DB row is `pending_approval`, `job["status"]` retains whatever the selection returned,
  and the recover branch fires unconditionally.

  Consequence: if `pending_approval` ever reaches the dispatcher (via a test harness,
  a future widening of `process_jobs_once`'s selection query, or direct call in a
  CI regression path), `process_recover` executes with `approved_at=None`. For a
  non-high-impact file this means `head_object` + `restore_object` fire before the
  owner-approval hold expires, incurring irreversible AWS cost and wrong-tier
  restores. `process_jobs_once` (lines 2313–2354) currently does not select
  `pending_approval` rows, so the gap is latent — but the dispatcher itself is the
  safety gate and it is missing the guard.
  Spec says: recover must execute only for status ∈ {queued, retrying, restoring}
  aligned with the selection query (REQ-002 condition 1).
  Code does: executes for any status the job dict carries.
  Confidence: high

- **Lines 2099–2102:** DIVERGENT [Req: REQ-004 — tier 5] `process_cloud_archive` issues
  an unversioned `delete_object`:

  ```python
  delete_result = s3_client().delete_object(
      Bucket=job["s3_bucket"],
      Key=object_key,
  )
  ```

  The scheduled `archive_version_id`'s `object_key` and `provider_version_id` are
  loaded from `archive_versions` at lines 2086–2093, but `delete_object` omits
  `VersionId`. S3 therefore creates a delete marker against whatever version is
  current at execution time, not the scheduled generation. A concurrent upload to
  the same key between queue and execute causes the newer version to be hidden
  without detection; the audit at lines 2107–2125 records the returned marker
  `VersionId` but narrates it as completing the intended archive of the queued
  context — a silent integrity failure.
  Spec says: must detect or abort when the current generation diverges from the
  scheduled expectation, or audit the actual marker target (REQ-004 conditions
  1–3).
  Code does: unversioned delete; no pre-delete generation comparison.
  Confidence: high

- **Lines 1622–1625:** DIVERGENT [Req: REQ-004 — tier 5] `process_rename` hides the
  old key using the same unversioned pattern:

  ```python
  delete_result = s3_client().delete_object(
      Bucket=job["s3_bucket"],
      Key=old_key,
  )
  ```

  After verifying the new key's content, the old key is hidden without VersionId,
  creating a delete marker on whatever is current at `old_key` at that moment.
  A concurrent write to `old_key` between the copy-verify step and this delete
  marker call would hide a version not intended for archival. REQ-004 condition 4
  explicitly names this as the same concurrent-writer hazard class as
  `process_cloud_archive`.
  Spec says: rename hide-old-key shares the same detection requirement as
  cloud-archive (REQ-004 condition 4).
  Code does: unversioned `delete_object` with no concurrent-write detection.
  Confidence: high

### app/services/metadata_backups.py + app/storage.py

- **metadata_backups.py lines 447–456 / storage.py lines 2578–2601:**
  DIVERGENT [Req: REQ-005 — tier 5] `_verify_postgres_dump_isolated` returns
  `{"ok": True, "verification_mode": "pg_restore_list"}` when `createdb` fails after
  `pg_restore --list` succeeds:

  ```python
  if created.returncode != 0:
      # Listing succeeded; treat as verified when a scratch DB cannot be created.
      return {
          "ok": True,
          ...
          "verification_mode": "pg_restore_list",
      }
  ```

  The caller `_verify_latest_metadata_backup_once` at `app/storage.py:2578` tests only:

  ```python
  if not result.get("ok"):
      raise metadata_backup_service.BackupError("Restore verification reported not ok")
  ```

  Because `ok` is `True` in the list-only path, this check passes.
  The code then executes lines 2590–2601 which update the backup run's DB record to
  `status='verified'`, `verified_at=<now>`. Operators and the API endpoint
  (`GET /api/admin/metadata-backups`) see `status='verified'` for a backup that was
  never restored into an isolated database; only the dump TOC was readable. During
  a real disaster recovery this gives false confidence: the dump may be structurally
  incomplete, the schema revision may not match, and user/vault counts are `None`
  in the returned dict (lines 451–454), all of which the operator never sees.
  Spec says: list-only mode must not be treated as full verify by consuming UIs or
  storage logic; degraded outcome must be distinct from isolated-restore success
  (REQ-005 conditions 2 and 4).
  Code does: `ok: True` propagates through consumer with no `verification_mode` check;
  backup row is promoted to `verified`.
  Confidence: high

### app/sessions.py

- **Lines 115–137 vs lines 95–96:** DIVERGENT [Req: REQ-008 — tier 5]
  `csrf_token_for` does not check `session_version` parity with the user record;
  `resolve_session` at line 95 does:

  ```python
  # resolve_session (line 95-96):
  if row["session_version"] != user["session_version"]:
      return None

  # csrf_token_for (lines 123-137): queries only revoked_at, idle_expires_at,
  # absolute_expires_at — no session_version join, no user table lookup.
  ```

  When an admin changes a user's password at `app/main.py:2691`:
  ```python
  updates.append("session_version=session_version+1")
  ```
  all of that user's existing sessions become invalid for `resolve_session` (which
  performs the version check). But `csrf_token_for` still returns the old CSRF
  token because it only reads from `sessions` without joining `users` for the
  version column. The CSRF middleware at `app/main.py:289–300` therefore accepts
  the revoked-by-version cookie's CSRF token before auth fails in `current_user` /
  `resolve_session`.

  In the current architecture every mutation endpoint uses `Depends(current_user)`
  which calls `resolve_session`, so auth still fails. The risk is defense-in-depth:
  any future mutation endpoint that trusts CSRF+cookie without `resolve_session`
  (e.g., a lightweight webhook handler or a middleware short-circuit) inherits a
  weaker gate where force-logout via session_version bump does not invalidate CSRF
  acceptance.
  Spec says: `csrf_token_for` should honor session_version revocation equivalently
  to `resolve_session` (REQ-008 condition 2).
  Code does: omits session_version join; revoked-by-version sessions still return a
  valid CSRF token.
  Confidence: high

  Confidence: high

## Non-findings (items verified to match spec)

The following scrutiny-area items were examined and found correct; no finding raised:

- **REQ-001** `download_exact_version_plaintext`: raises on empty `provider_version_id`
  (line 1825–1826); plaintext path uses boto3 `VersionId` (line 1861); crypt/name-encrypt
  path passes `--s3-version-id={provider_version_id}` rclone flag (line 1830); digest
  mismatch raises RuntimeError without promoting local presence (lines 2041–2044).

- **REQ-006** `is_break_glass_allowed` (breakglass.py:30–48): fails closed on
  `None`/unparseable IP (lines 36–41); loopback always allowed (lines 42–43);
  empty CIDRs → loopback-only; bad CIDR parse returns False (lines 44–48). Correct.

- **REQ-007** `resolve_client_ip` (proxy.py:28–48): untrusted peer → returns peer
  (line 42–43); trusted peer + XFF → rightmost untrusted hop (lines 44–47);
  all hops trusted → `hops[0]` (line 48); missing peer → `None` (lines 40–41). Correct.

- **REQ-009** `process_free_space` (storage.py:1700–1759): claim via rename (line 1741);
  failed rehash caught by `except Exception as exc:` (line 1754) which calls
  `restore_claimed_local_copy` (line 1755); restore failure raises RuntimeError
  referencing `claimed_path` (lines 1756–1758); `OperationCancelled` (subclass of
  `RuntimeError`/`Exception`) is also caught and triggers restore before propagating.
  Correct.

- **REQ-010** `initialize_database` (database.py:100–104): raises `DatabaseSchemaError`
  with message referencing `alembic upgrade head` when revision ≠
  `HEAD_SCHEMA_REVISION` (`"0021_local_retention"`, line 16). SQLite and PostgreSQL
  both check version table. Correct.

- **REQ-011** `require_upload_custody` (vault_recovery.py:145–149): raises
  `RecoveryCustodyRequired` when `vault_requires_recovery_custody(vault)` is True.
  Message does not include secret material. Correct.

- **REQ-012** `_normalize_windows` (operation_policies.py:96–97): raises `ValueError`
  when `start >= end`. Correct.

- **REQ-013** `process_cloud_purge` (storage.py:2161–2164): versioned
  `delete_object(Bucket=…, Key=…, VersionId=item["provider_version_id"])`. Correct.

- **REQ-014** `list_rename_candidates` (catalog.py:493–508): `decision="auto"` only
  when `len(missing_rows)==1 and len(present_rows)==1`; `"ambiguous"` otherwise.
  Correct.

- **REQ-015** `current_vault` (main.py:434–468): joins `vault_members` and requires
  `v.enabled=TRUE`; stale `vault_id` in session falls back to first assigned vault
  (line 452–462) or raises 403. Correct.

- **REQ-016/017** `can_operate` / `is_owner` (vault_roles.py:27–39): `can_operate`
  returns True for owner+operator only; viewer denied; `/api/recover` and `/api/upload`
  enforce `can_operate`; `/api/free-space` enforces `is_owner`. Correct.

- **REQ-018**: Two-layer architecture confirmed — HTTP gate (`main.py:2451–2452`) plus
  worker fingerprint/VersionId gate (`storage.py:1705–1759`). Correct.

- **REQ-019**: `docs/filesystem-permissions.md` exists and documents source_root /
  data path permission requirements. No code path contradicts it.
