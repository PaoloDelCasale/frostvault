# BUG-001: process_job recover branch lacks status whitelist

> Generated by [Quality Playbook](https://github.com/andrewstellman/quality-playbook) v1.5.6 — Andrew Stellman
> Date: 2026-07-23 · Project: FrostVault

## 1. Summary

The job dispatcher runs recover without an explicit status conjunct, unlike every peer action.

## 2. Spec reference

- Requirement: REQ-002
- Behavioral contract quote: "recover only for queued|retrying|restoring"
- REQ-002 requires recover only for `{queued, retrying, restoring}`; peer branches at `app/storage.py:2219-2232` encode that whitelist pattern.

## 3. The code

`elif job["action"] == "recover":\n    process_recover(job)` at `app/storage.py:2223-2224` — no status check.

## 4. Observable consequence

A recover Job whose DB status is outside the poll set (or a stale queued dict after status advanced) can still enter `process_recover`, including RestoreObject / download side effects.

## 5. Depth judgment

Selection in `process_jobs_once` currently filters statuses, so the gap is latent under today's query — but the dispatcher is the last safety gate and peers already implement it.

## 6. The fix

Proposed change from `quality/workspace/patches/BUG-001-fix.patch`:

```diff
diff --git a/app/storage.py b/app/storage.py
index c548cc0..fa53197 100644
--- a/app/storage.py
+++ b/app/storage.py

             process_upload(job)
         elif job["action"] == "rename" and job["status"] == "queued":

-        elif job["action"] == "recover":
+        elif job["action"] == "recover" and job["status"] in {"queued", "retrying", "restoring"}:
```
